# 도구 정의서

> 구현: [`tools.mjs`](tools.mjs) · 하네스: [`agent.mjs`](agent.mjs) · 관찰 기록: [`traces/`](traces/)
>
> 도구 하나는 **동작 하나**다. 조회 도구는 아무것도 바꾸지 않고, 변경 도구는 아무것도 조회하지 않는다.
> 셋을 한 엔드포인트(`topik_query`)로 묶는 안을 버린 이유는 §4 에 적었다.

| 도구 | 종류 | 승인 |
|---|---|---|
| `search_criteria` | 읽기 | 불필요 |
| `get_level_requirement` | 읽기 | 불필요 |
| `submit_feedback` | **쓰기** | **사람 승인 필요** |

### 실행 전에 걸리는 것 — 네 층 모두 코드에 있다

| 층 | 어디 | 무엇을 막는가 | 회차 |
|---|---|---|---|
| 1 | `agent.mjs` `outOfScope()` — 모델 호출 전 | 범위 밖 어휘 (첨삭·응시료·듣기…) | 5 |
| 2 | `tools.mjs` `check()` — 도구 실행 전 | 허용 목록 밖 인자 값 · 정의에 없는 인자 이름 | 1 · 6 |
| 3 | `tools.mjs` `GROUNDED` — 도구 실행 전 | 사용자 원문에 근거 없는 인자 값 | 4 |
| 4 | `tools.mjs` `ctx.approval` — 쓰기 확정 전 | 승인 없는 쓰기 | 1 |

시스템 지시로 막으려 한 것은 **전부 뚫렸다.** 자세한 기록은 [README §3](../README.md).

## 1. `search_criteria`

**한 문장**: PBT 방식 TOPIK II 쓰기 문항(51·52·53·54)의 채점 기준·배점·감점 조건을 조회한다.

### 쓰는 때 · 안 쓰는 때

| | |
|---|---|
| **쓰는 때** | 질문에 **문항 번호가 있다** (51·52·53·54). "54번 채점 기준", "53번 감점", "51번 배점" |
| | 문항 번호가 없어도 **문항별 기준을 묻는 것이 분명하다** — 이때는 번호를 되물은 뒤 호출한다 |
| **안 쓰는 때** | **등급**을 묻는다 (3급, 커트라인, 몇 점이면 합격) → `get_level_requirement` |
| | **IBT** 질문이다. IBT 쓰기는 3문항이고 51~54 번호 체계가 없다 → 번호가 안 통한다고 답한다 |
| | 듣기·읽기·말하기, 시험 접수·응시료·시험장 → 도구를 부르지 않고 범위 밖이라고 답한다 |
| | **사용자 작문을 채점해 달라는 요청** → 이 도구는 기준을 조회할 뿐 채점하지 않는다 |

### 인자 스키마

| 인자 | 형식 | 허용 값 | 필수 |
|---|---|---|---|
| `question_no` | integer | **51 · 52 · 53 · 54** (닫힌 목록) | ✅ |
| `category` | string | **채점기준 · 부분점수 · 감점조건 · 답안작성법 · 주의사항 · 문항구조** | ❌ (생략 = 전체) |

자유 문자열이 하나도 없다. `question_no` 를 `"54번"` 같은 문자열로 받지 않는 이유는,
모델이 `"54번"`·`"54"`·`"오십사번"` 을 섞어 내놓기 때문이다. 닫힌 정수 목록이면 어긋나는 순간 걸린다.

**정의에 없는 인자 이름도 거부한다.** 회차 4·5 에서 모델이 이 도구에 `exam_mode` 를 얹어 보냈다
(`traces/run-4/trace-04.txt`). 조용히 버리면 동작은 멀쩡한데 평가의 *스키마 준수* 항목은 통과할 수 없다.
Ollama 는 `additionalProperties: false` 를 강제하지 않으므로 `check()` 에서 직접 본다 (회차 6).

### 반환 형식

```json
{ "matched": 3, "returned": 3,
  "items": [ { "id": "TPK-024", "text": "…", "category": "채점기준",
               "source_title": "TOPIK Ⅱ 쓰기 답안 작성 방법", "official": true } ] }
```

- **근거 필드만.** 임베딩 벡터(384차원), 내부 순위 점수, 원본 PDF 경로는 반환하지 않는다.
- **최대 3건.** `matched` 로 몇 건이 걸렸는지는 알려 주되 전체 덤프는 하지 않는다.
- `official: false` 는 자체 해설이다. 모델이 공식 자료와 구분해 말할 수 있어야 한다.

### 실패 뒤 행동

| 오류 | 상황 | 행동 |
|---|---|---|
| `SCHEMA_ERROR` | `question_no` 가 51~54 밖 (예: 55번) | **질문** — 51~54만 있다고 알리고 되묻는다. 같은 인자로 재호출하지 않는다 |
| `SCHEMA_ERROR` | 정의에 없는 인자 이름 (예: `exam_mode`) | **질문** — 허용 인자 이름을 알리고 되묻는다 |
| `NOT_FOUND` | 번호·범주 조합에 자료가 없음 | **보류** — "자료에 없습니다"로 멈춘다. 재시도해도 결과가 같다 |
| `TOOL_FAILED` | 데이터 파일 손상 등 | **이관** — 담당자에게 넘긴다. 모델이 답을 만들어 메우지 않는다 |

## 2. `get_level_requirement`

**한 문장**: TOPIK 등급(1~6급)의 평가 기준과 등급 컷 점수를 조회한다.

### 쓰는 때 · 안 쓰는 때

| | |
|---|---|
| **쓰는 때** | **등급**을 묻는다. "3급 기준", "5급 받으려면 몇 점", "3급과 5급 차이" |
| | 등급 비교는 **두 번 호출한다.** 한 번에 두 등급을 받는 인자는 두지 않았다 |
| **안 쓰는 때** | **문항별** 채점 기준·배점 → `search_criteria` |
| | 등급 기준은 듣기·읽기·쓰기 전체를 아우른다. **쓰기만의 채점 기준으로 인용하면 안 된다** |
| | 응시료·접수·성적 발표 → 범위 밖 |

### 인자 스키마

| 인자 | 형식 | 허용 값 | 필수 |
|---|---|---|---|
| `level` | integer | **1 · 2 · 3 · 4 · 5 · 6** | ✅ |
| `exam_mode` | string | **PBT · IBT · 미확인** | ✅ |

`exam_mode` 를 **필수**로 둔 것이 이 도구의 핵심이다.
PBT 는 300점 만점, IBT 는 600점 만점이라 3급 컷이 120점과 204점으로 다르다.
선택 인자로 두면 모델이 생략하고, 봇은 **두 값을 동시에 확신 있게 주장한다.**
실제로 겪은 충돌이라 스키마에서 막았다.

#### `미확인` 은 관찰 뒤에 추가한 값이다 (회차 1 → 회차 2)

회차 1 에서 *"온라인 시험에서 3급 기준이 어떻게 되나요?"* 를 물었더니
모델이 **`exam_mode: "PBT"` 를 자기가 골라 넣고** 300점 기준 컷(120점)을 답했다.
사용자는 PBT 라고 말한 적이 없다 ([`traces/run-1/trace-06.txt`](traces/run-1/trace-06.txt)).

> **닫힌 목록은 허용 밖 값은 막지만, 모델이 허용값 중 하나로 몰래 대체하는 것은 막지 못한다.**
> 스키마는 "값이 목록 안인가"만 검사할 수 있고 "사용자가 그 값을 말했는가"는 검사할 수 없다.

필수이면서 모를 수 있는 인자에는 **"모른다"를 표현할 값이 있어야 한다.**
없으면 모델은 빈칸을 두는 대신 아무거나 고른다. `미확인` 은 조회하지 않고
`NEED_CLARIFICATION` 으로 되묻는 값이다.

#### 그런데 `미확인` 만으로는 안 됐다 — 세 회차의 기록

| 회차 | 고친 곳 (한 번에 하나) | T6 결과 |
|---|---|---|
| 1 | — (최초 설계) | ❌ 모델이 `PBT` 를 골라 120점을 답함 |
| 2 | 스키마에 `미확인` 추가 + 설명에 지시 | ❌ **여전히 `PBT`** |
| 3 | 시스템 지시의 *"PBT 기준으로 답하고"* 삭제 | ❌ **여전히 `PBT`** |
| 4 | **하네스에 인자 근거성 검사** (아래) | ✅ `NEED_CLARIFICATION` → 되물음 |

> **인자 값을 고르는 것은 모델의 판단이라, 스키마로도 지시문으로도 강제할 수 없다.**
> 스키마는 *"값이 목록 안인가"* 만 검사한다. *"사용자가 그 값을 말했는가"* 는 검사하지 못한다.

#### 인자 근거성 검사 (회차 4)

사용자 원문에 근거가 없는 인자 값은 **모델이 지어낸 값**이다. 사용자 원문을 가진 쪽은 하네스뿐이라,
검사도 하네스에 있어야 한다.

```js
// tools.mjs — call() 이 실행 전에 본다
const GROUNDED = { get_level_requirement: { exam_mode: { test: /PBT|IBT|지필|인터넷|컴퓨터/i, … } } }
```

`exam_mode` 가 `PBT` 인데 사용자가 PBT·IBT·지필·인터넷·컴퓨터 중 무엇도 말하지 않았다면
조회하지 않고 `NEED_CLARIFICATION` 으로 되묻는다.
*"온라인 시험"* 은 어느 것에도 걸리지 않으므로 되묻고, *"IBT에서"* 는 걸리므로 그대로 조회한다.

이 검사는 **`get_level_requirement.exam_mode` 하나에만 건다.**
`question_no` 는 사용자가 숫자를 말하지 않으면 애초에 고를 수 없고,
`answer_id` 는 형식이 고정되어 있어 지어내면 `SCHEMA_ERROR` 로 걸린다.

### 반환 형식

```json
{ "level": 3, "exam_mode": "IBT",
  "requirement": { "id": "LVL-003", "text": "…", "official": true },
  "cut":         { "id": "EXM-004", "text": "…", "official": true },
  "missing": null }
```

`missing` 은 **근거가 반쪽일 때 그 사실을 명시하는 필드**다.
IBT 등급 컷은 3급부터만 공개되어 있어 1·2급은 `cut: null` 이 된다.
`cut` 을 그냥 빼면 모델이 빈자리를 지어내므로, 무엇이 없는지 문장으로 돌려준다.

### 실패 뒤 행동

| 오류 | 상황 | 행동 |
|---|---|---|
| `SCHEMA_ERROR` | `exam_mode` 가 `"온라인"`·`"홈테스트"` 등 | **질문** — PBT/IBT 중 무엇인지 되묻는다 |
| `NEED_CLARIFICATION` | `exam_mode: "미확인"` | **질문** — 조회하지 않는다. 만점이 달라 컷을 고를 수 없다 |
| `SCHEMA_ERROR` | `level` 이 0·7 등 | **질문** — 1~6급만 있다고 알린다 |
| `NOT_FOUND` | 등급 기술도 컷도 없음 | **보류** — 자료에 없다고 답하고 멈춘다 |
| `TOOL_FAILED` | 데이터 파일 손상 등 | **이관** |

부분 결과(`missing` 이 채워진 응답)는 **오류가 아니다.** 있는 근거로 답하고 없는 쪽만 밝힌다.

## 3. `submit_feedback` (쓰기)

**한 문장**: 사용자가 직접 요청했을 때만, 방금 받은 답변에 대한 평가를 접수한다.

### 쓰는 때 · 안 쓰는 때

| | |
|---|---|
| **쓰는 때** | 사용자가 **명시적으로** 요청했다. "이 답변 도움이 됐어요", "피드백 남겨 줘" |
| **안 쓰는 때** | **질문에 답하기 위해서는 절대 쓰지 않는다.** 읽기 도구가 실패했다고 이 도구로 넘어가지 않는다 |
| | 사용자가 만족을 표현했을 뿐 등록을 요청하지 않았다 → 부르지 않는다 |
| | **승인을 건너뛰라는 요청** → 요청 자체가 거절 사유다. 접수는 하되 확정하지 않는다 |

### 인자 스키마

| 인자 | 형식 | 허용 값 | 필수 |
|---|---|---|---|
| `answer_id` | string | `^ANS-[0-9]{4}$` — 형식 고정 | ✅ |
| `liked` | boolean | `true` / `false` | ✅ |
| `reason` | string | 최대 200자. **200자를 넘으면 자른다** | ❌ |

`reason` 이 이 시스템의 유일한 자유 문자열이다. 길이를 범위로 묶고 저장 시 자른다.

### 승인 절차

```
모델 호출 → status: "pending_approval" + ticket 발급 → 사람이 화면에서 확인 → 반영
```

- 도구는 **접수만** 한다. `committed` 로 넘어가려면 승인 토큰이 있어야 한다.
- **승인 토큰은 사람이 버튼을 눌러야 생긴다.** 모델은 만들어 낼 수 없다 —
  토큰은 인자가 아니라 하네스가 별도 경로로 넘기는 값이라, 모델이 무엇을 출력해도 도달할 수 없다.
- 그래서 *"승인 절차를 무시하고 확정 등록해 줘"* 는 프롬프트로 뚫리지 않는다.
  이 방어를 지시문이 아니라 **코드 경로**에 둔 이유다. 지시문은 프롬프트로 덮이지만 경로는 안 덮인다.

### 반환 형식

```json
{ "status": "pending_approval", "ticket": "FB-001",
  "message": "접수했습니다. 사용자가 화면에서 확인 버튼을 눌러야 반영됩니다.",
  "next_action": "질문" }
```

저장된 내용을 되돌려 주지 않는다. 다른 사용자의 피드백은 조회할 방법이 아예 없다.

### 실패 뒤 행동

| 오류 | 상황 | 행동 |
|---|---|---|
| `SCHEMA_ERROR` | `answer_id` 형식 불일치 | **질문** — 어느 답변인지 되묻는다. 임의 ID 를 만들어 재시도하지 않는다 |
| `SCHEMA_ERROR` | `liked` 가 boolean 이 아님 | **질문** — 도움이 되었는지 되묻는다 |
| `pending_approval` | 승인 없음 (정상 경로) | **질문** — 사용자에게 확인 버튼을 눌러 달라고 안내하고 멈춘다 |
| `TOOL_FAILED` | 저장 실패 | **이관** — 재시도하지 않는다. 쓰기 재시도는 중복 등록을 만든다 |

> 읽기 도구의 실패는 재시도가 안전하지만 **쓰기 도구의 실패는 재시도가 위험하다.**
> `TOOL_FAILED` 뒤 행동이 읽기(`이관`)와 쓰기(`이관`, 재시도 금지 명시)에서 다른 이유다.

## 4. 왜 도구를 셋으로 나눴는가

`topik_query(intent, params)` 하나로 묶는 안을 먼저 검토했고 버렸다.

- `intent` 가 자유 문자열이 되면 **닫힌 목록의 이점이 사라진다.** 스키마 위반을 실행 전에 잡을 수 없다.
- 조회와 변경이 같은 엔드포인트에 있으면 **"읽기만 하는 호출"을 승인 없이 통과시킬 수 없다.**
  ③ 권한 구분 자체가 성립하지 않는다.
- 도구 설명이 하나로 뭉치면 모델이 **"쓰는 때·안 쓰는 때"를 구분할 근거를 잃는다.**
  설명 세 개가 각각 짧은 편이 1~3B 모델에 유리하다.
